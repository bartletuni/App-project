## 2025-05-13 - [CRITICAL] Fixed Insecure Direct Object Reference (IDOR) on File Downloads
**Vulnerability:** The API endpoint `/api/download/[fileId]` verified if a user was authenticated, but completely missed verifying if that user was actually authorized to access the specific file. This means any authenticated user could iterate or guess `fileId` values to download other users' uploaded 3D printing STL models.
**Learning:** This vulnerability existed because the authorization check was only verifying session presence, not session authority over the requested resource. When dealing with file downloads via cloud storage (Cloudflare R2), checking identity isn't enough; we must query the database to correlate the requested `fileId` with the `userId` that owns it before generating the presigned S3 URL.
**Prevention:** Ensure all API routes that fetch or manipulate specific resources (like downloads by ID) perform a database lookup or metadata check to assert that `resource.ownerId === currentUser.id` (or the user is an admin) before returning sensitive data.
## 2025-05-14 - [CRITICAL] Prevented Data Leakage of User Password Hashes via Prisma Relation Include
**Vulnerability:** The API endpoints `/api/requests` and `/api/requests/[id]` fetched part request information and explicitly loaded the associated user with `include: { user: true }`. Because Prisma returns all fields by default, this effectively exposed sensitive user data—namely hashed passwords and potentially other billing details—in API responses to both standard users and administrators.
**Learning:** Using `include: { relation: true }` in Prisma is dangerous when the related entity contains sensitive information (like user credentials). Prisma does not have automatic "hidden" fields.
**Prevention:** Always explicitly define which fields are safe to return when fetching relations. Use nested `select` statements inside the include block (e.g., `user: { select: { id: true, email: true } }`) to explicitly whitelist fields and prevent data leakage.
## 2025-05-15 - [MEDIUM] Added Missing Input Validation to User Registration
**Vulnerability:** The `/api/auth/register` endpoint accepted any string as an email and any length string as a password, allowing users to be created with malformed emails and weak passwords.
**Learning:** The password strength requirement (minimum 6 characters) was enforced during password changes (`/api/user/change-password`), but not during initial user creation, creating an inconsistent security posture.
**Prevention:** Always implement strong, consistent input validation (e.g., regex for emails, minimum length for passwords) at all entry points that accept user data, especially authentication and registration routes.
## 2025-05-16 - [HIGH] Fixed HTML Injection / XSS in Email Templates
**Vulnerability:** The email template generation function in `src/lib/email-templates.ts` (`NewRequestEmailHTML`) was manually constructing HTML strings and directly interpolating user input (names, file names, notes) without any escaping or sanitization. This allowed an attacker to inject arbitrary HTML, CSS, or scripts into the emails sent to administrators.
**Learning:** This vulnerability existed because the application relied on manual string concatenation for HTML generation instead of a proper templating engine (like Handlebars or React Email) that automatically escapes variables by default.
**Prevention:** When manually constructing HTML strings that include user input, always sanitize or escape the input using a dedicated escaping function (e.g., replacing `<`, `>`, `&`, `"`, `'` with their HTML entities) before interpolation. Alternatively, use modern templating libraries that provide automatic escaping to prevent injection flaws.

## 2026-05-25 - [CRITICAL] Fixed Path Traversal in File Uploads
**Vulnerability:** The application was uploading user-provided files to Cloudflare R2 using the original `file.name` concatenated directly with a timestamp as the object key. The only substitution was replacing spaces with underscores (`fileName.replace(/\s+/g, "_")`). An attacker could provide a malicious filename containing path traversal sequences (e.g., `../../../malicious.txt`) or illegal characters to attempt directory escapes or disrupt the S3 bucket structure.
**Learning:** This vulnerability existed because we trusted the user-provided filename from the `FormData` boundary. File systems and cloud storage APIs may interpret certain characters (like `/`, `\`, `..`) as directory separators, potentially allowing attackers to overwrite files outside the intended namespace.
**Prevention:** Always sanitize user-provided filenames before using them as object keys or file system paths. Use a strict allowlist regex (e.g., `[^a-zA-Z0-9.\-_]`) to strip any potentially dangerous characters, and ensure a fallback string (like `"unnamed_file"`) is used if the entire filename is stripped.

## 2026-05-26 - [HIGH] Fixed Content-Type Spoofing and Stored XSS
**Vulnerability:** The API endpoints for uploading part requests (`/api/requests/route.ts`) and material images (`/api/admin/materials/route.ts` and `/api/admin/materials/[id]/route.ts`) trusted the user-provided `file.type` from `FormData` to set the MIME type when uploading files to Cloudflare R2. An attacker could upload a malicious HTML file but provide an acceptable extension (e.g., `.png`) and the MIME type `text/html`. If another user downloaded and opened the file, their browser would execute the HTML, leading to Stored XSS.
**Learning:** This vulnerability existed because the application trusted the `file.type` attribute provided by the client, which is trivial to spoof. Security should never rely on client-provided metadata without server-side validation.
**Prevention:** Always infer the MIME type server-side based on the verified file extension or magic bytes, rather than trusting the user-provided `file.type`. Ensure strict validation of allowed file extensions before accepting an upload.

## 2024-06-10 - Unbounded Fields and Default Prisma Int Handling
**Vulnerability:** The application allowed negative values for the `quantity` field and unbounded string lengths for `notes` and `phoneNumber` fields, presenting both business logic flaws (e.g. requesting -10 parts) and Denial of Service (DoS) risks (e.g. sending GBs of text in a notes field).
**Learning:** Prisma allows any integer for an `Int` field by default. Relying on frontend HTML constraints (e.g., `<input type="number" min="1">`) is insufficient as API endpoints can be directly hit. Additionally, unbounded text fields expose the database and server to exhaustion attacks.
**Prevention:** Always validate numeric bounds explicitly at the application level before passing data to Prisma. Similarly, strictly enforce sensible maximum length limits on all user-provided strings at the API layer.
## 2024-06-25 - [HIGH] Enforced Strong Password Complexity
**Vulnerability:** The password requirements for user registration (`/api/auth/register`) and password changes (`/api/user/change-password`) were exceedingly weak, only enforcing a minimum length of 6 characters without requiring any complexity (uppercase, lowercase, numbers, or special symbols). This exposes user accounts to brute-force and dictionary attacks.
**Learning:** Checking just `password.length < 6` is not sufficient for modern authentication security. Lack of complexity makes passwords predictable and easily cracked.
**Prevention:** Implement strict password complexity rules. Enforce a minimum length of at least 8 characters and require a mix of uppercase letters, lowercase letters, numbers, and special characters using robust regular expressions (e.g., `/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[\W_]).{8,}$/`). Apply this validation consistently on both frontend forms and backend API routes.
